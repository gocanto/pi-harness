## 1. How to read this

- **Evidence** cites `file:line` (this worktree, base `3eac49c`). Re-verify
  against source before relying on a cell — this is a compatibility contract
  snapshot, not a guarantee (see Maintenance note).
- **Unknown** means: not measurable from this repository without live

## 3. User-facing policy

### 3.1 What is common vs. backend-specific

Common (identical across all three backends, enforced by the manager rather
than the backend): the concurrency cap, transcript/output size budgets, the
kill-on-parent-shutdown persistence policy, and the trust boundary that gates
autonomous host access.

Backend-specific by design, and this is the part a user picking a harness
needs to know up front:

- **Steering.** Only pi and Claude Code let a live message land inside the
  current turn. Codex always defers a `send()` while active to a follow-up
  turn. This is exposed today as `capabilities.steering` per backend
  (`src/backend.ts:22-27`) but nothing in the model-facing tool description
  (`src/prompt.ts`) or the `subagent_wait`/`subagent_check` output tells the
  parent model _which_ backend it picked has this limitation — see backlog
  item B1.
- **Model/effort granularity.** Codex clamps the requested reasoning effort to
  whatever the resolved model actually supports (`supportedCodexEffort`);
  Claude and pi apply the requested value unconditionally (Claude only clamps
  implicitly via the 0–63,999 token budget table; pi has no clamping at all
  since the scale is native).
- **Context window discovery.** Claude starts with a hardcoded 200k fallback
  until the CLI reports otherwise mid-run; Codex and pi report the real
  window from the start (registry lookup / app-server notification). A user
  reading the very first status line for a Claude subagent before its result
  message could see a stale window value.

### 3.2 How unsupported options fail

No backend rejects a `subagent_spawn` call for requesting an option it does
not support — there is no per-backend request validation in `index.ts`'s tool
schema. Instead, unsupported behavior silently degrades:

- Steering into a Codex subagent never throws; it queues as `"follow-up"` and
  the model sees a normal `QueueChanged` event, indistinguishable in shape
  from a genuine steer on pi/Claude. The only user-visible signal is that the
  subagent's queue entry says "follow-up" instead of "steer" if the UI
  renders that distinction (`src/domain.ts:117-120` `QueuedMessage.kind`).
- An unresolvable `model` hint fails at spawn time for pi (`resolvePiModel`
  throws `Unknown model "..."`, becomes a `SpawnError`) but for Claude/Codex
  is passed through uninterpreted to the SDK/CLI, which decides whether to
  error or substitute a default — this repo does not validate the string
  against either provider's model list before spawning (Codex's
  `model/list` probe only runs to clamp reasoning effort, not to validate the
  model itself).
- Backend unavailability (binary missing) is the one case that _does_ fail
  fast and distinctly, as a `BackendUnavailableError` before any concurrency
  slot is reserved (`src/manager.ts:450-455`) — but, per §2 above, "available"
  only checks the binary is on `PATH`, not that it is authenticated. A
  present-but-logged-out CLI would instead fail later, mid-spawn, as a
  generic `SpawnError` with whatever message the SDK/app-server produced.

### 3.3 Security implications

- The trust boundary (`resolveStandaloneChildProjectTrust`,
  `extensions/shared/child-session.ts`, exercised by `trust.test.ts`) is the
  single gate all three backends share: same-cwd-as-parent inherits the live
  parent trust decision, a different cwd requires an explicit saved trust
  entry, and anything unresolvable (including a nonexistent directory) fails
  closed as untrusted. This check runs in `index.ts` **before** the manager
  reserves a concurrency slot or a backend is touched
  (`index.ts:290-302`), so an untrusted `working_dir` never reaches a backend
  capable of granting autonomous access.
- Both native backends keep `approvalPolicy`/interactive-prompt handling
  fixed regardless of trust (Claude's `dontAsk`, Codex's `"never"` +
  auto-decline) because a headless child can never answer an interactive
  prompt either way; **only** the sandbox/permission mode itself
  (`bypassPermissions` vs `dontAsk`; `danger-full-access` vs
  `workspace-write`) is what trust actually gates. `permission-policy.test.ts`
  asserts the untrusted branch never returns the trusted values for either
  backend, closing the most likely regression (a trust flag accidentally
  defaulting to the permissive branch).
- No backend's `available` probe confirms authentication (§2, "Failure mode
  when unauthenticated"). This is not a security hole per se (an
  unauthenticated CLI cannot act), but it does mean the fast-fail UX promised
  by "resolved open question 7" in `design-plan.md` (§8, row 7) only covers
  the binary-missing case, not the credentials-missing case.

### 3.4 Recommended default harness/model behavior

- Keep pi as the recommended default harness (already reflected in
  `SUBAGENT_SPAWN_PROMPT_GUIDELINES`, `src/prompt.ts:12-16`: "pi unless you
  have a reason to prefer Claude Code or Codex") — it is the only backend with
  zero credential/binary risk, the only one that inherits the parent's
  model/effort by default, and the only one with true steering plus the
  lowest structural spawn latency.
- Do not change Claude/Codex's "omit model = provider default" behavior. Pi's
  inheritance is only possible because it shares the parent's own
  `ModelRegistry` in-process; Claude/Codex spawn a separate CLI/process with
  no equivalent inheritance channel today, and building one is out of this
  spike's scope (see backlog item B3).

## 4. One-shot mode: worth a separate API?

**Recommendation: reject, for now.** A dedicated cheap "one-shot" spawn
(`exec(task): Effect<RunOutcome>` per `design-plan.md` §8 row 2, historically
proposed and never built) would only pay off if it removed real overhead:

- For **pi**, there is no overhead to remove — it's already an in-process
  session; a one-shot mode would just be `spawn` + `waitFor` with no
  process/handshake cost either way.
- For **Claude Code**, the existing path is already a single `query()` call;
  a one-shot variant would save the streaming-input bridge (`ClaudeInput`)
  but that bridge is cheap in-process bookkeeping, not an external cost.
- For **Codex**, one-shot mode's savings would be real (skip the persistent
  `codex app-server` child + `initialize`/`thread/start` handshake per run)
  but Codex is also the only backend where that handshake cost is currently
  **unmeasured** in this repo (§2, Latency row) — proposing a new API to
  optimize an unmeasured cost is exactly the kind of change this spike should
  not force.

**Rejection criteria for a future one-shot proposal:** do not build it unless
a follow-up plan can show (a) measured per-spawn overhead for at least the
Codex path that is large relative to typical subagent task duration, and (b)
a concrete user-facing scenario (e.g. rapid-fire trivial delegations) that
current `subagent_spawn`/`subagent_wait` cannot serve acceptably. Absent
both, the two-tool surface (`spawn` + `wait`) already covers the "cheap
one-shot" use case adequately by waiting immediately after spawn.

## 6. Open questions for maintainer input

These require a product/cost decision this spike cannot make on its own:

1. Is the Claude 200k context-window fallback (`CLAUDE_CONTEXT_WINDOW`,
   `src/backends/claude.ts:38`) worth replacing with an upfront model-capacity
   lookup, or is "corrects itself after the first result message" acceptable
   given how briefly the fallback is visible?
2. Should `subagent_spawn` reject harness/model/effort combinations it can
   already tell won't do what the caller likely expects (e.g. requesting
   steering-sensitive workflows on Codex), or is silent degradation (§3.2)
   the intended UX?
3. Is B5 (spawn-latency/cost telemetry) worth building at all given pi
   product telemetry policy, or should latency/cost stay permanently
   "Unknown" in this matrix?
